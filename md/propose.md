# 병원 전산 관리직 지원 포트폴리오 제안서

2026-07-17 · 대상: 병원 전산실/의료정보팀 지원자 · 전제: 1인 제작, 실환자 데이터 미사용

---

## 요약

**"Hospital FHIR Ops Lab" — 합성 병원 데이터로 만든 미니 연계 시스템 + 운영 증빙 기록집.**

가짜 병원(합성 HIS 데이터베이스)을 하나 세우고, 그 데이터를 의료정보 표준 **FHIR R4**로
변환·조회하는 작은 연계 시스템을 만듭니다. 단, 이 포트폴리오의 주인공은 기능이 아니라
**운영 기록**입니다 — 장애를 일부러 내고 잡은 로그북, 배치가 실패했을 때의 재처리 절차,
느린 SQL을 튜닝한 전후 비교, 백업·복구 리허설. "개발을 해봤다"가 아니라 **"시스템을 운영해
봤다"를 증명**하는 구성입니다.

## 1. 왜 이 포트폴리오인가

- **직무의 실체와 맞습니다.** 병원 전산직의 실제 업무는 EMR/OCS/HIS 같은 기존 시스템의
  운영·유지보수가 중심입니다(채용 공고·현직자 실측). 화려한 신규 개발 포트폴리오는 오히려
  "우리 일과 다른 걸 하고 싶어하는 사람"으로 읽힐 수 있습니다. 장애 대응·SQL·백업을 다뤄본
  흔적이 면접에서 통하는 언어입니다.
- **최신 트렌드에 정면으로 닿습니다.** FHIR R4는 글로벌 표준이 됐고(EHR 벤더 92% 지원),
  국내도 EMR 인증제 2주기가 FHIR 표준 기능을 강화하는 방향이며 마이헬스웨이(의료 마이데이터)
  가 기관 간 정보 교류를 확대 중입니다. "레거시 병원 DB를 표준으로 연결해 본 사람"은 흔치
  않아 즉시 차별화됩니다.
- **혼자서 끝까지 완성할 수 있습니다.** 합성 데이터 + 단일 DB + Docker Compose 로컬 실행이라
  비용·법적 리스크가 없고, 산출물에 우선순위(P0/P1/P2)를 둬서 "다 못 만들어서 미완성"이 되는
  것을 방지합니다.

## 2. 기술 스택

| 계층 | 스택 | 선택 이유 |
|---|---|---|
| 백엔드 | Java 17 + Spring Boot 3.x (+Spring Batch, MyBatis 또는 JPA) | 병원·SI 채용 코딩시험의 실제 출제 언어. FHIR는 HAPI FHIR의 구조체 라이브러리만 사용(무거운 전체 서버는 배제) |
| DB | **MySQL 8.x 단일** (기본) — 대형병원 지원 시 Oracle 19c 버전을 별도 분기 문서로 | 채용 SQL 시험이 "Oracle/MySQL 택1". 두 DB 동시 운용은 1인 범위에서 복잡도만 늘려 배제 |
| 프론트 | 옵션 A: React 18 + TypeScript 5 / 옵션 B: Thymeleaf + AdminLTE | §5 선택 옵션 참조 |
| 인프라 | Docker Compose + Nginx (클라우드·K8s 미사용) | 로컬에서 완성·시연 가능. 병원 폐쇄망 현실과도 맞음 |
| 관측 | Prometheus + Grafana | 장애 시나리오 시연에 필요충분. 관측 도구를 늘리는 건 과투자 |
| 인증·인가 | Spring Security 폼·세션 로그인 + 역할 기반 접근제어(RBAC) | 별도 인증 서버(IdP) 없는 구성에서 가장 정직하고 단순한 설계 |
| 마이그레이션·테스트 | Flyway(제한 사용), JUnit 5 | 스키마 이력 관리의 기본기만 |
| 데이터 | Synthea 등 공개 합성 환자 데이터 생성기 | 실환자 데이터 금지 전제의 유일한 안전한 선택 |

## 3. 설계서

### 3.1 시스템 아키텍처

```
[합성 레거시 HIS DB (MySQL 8.x)]   ← 정본. Synthea 산출 데이터 적재
        │  Spring Batch 배치 pull: 워터마크 기반 증분 + 멱등 upsert
        │  (CDC·실시간 동기화는 의도적으로 배제 — 1인 범위·병원 배치 문화와 정합)
        ▼
[연계 서비스 (Spring Boot)]
   ├─ FHIR 변환 계층 : 레거시 스키마 → FHIR R4 JSON
   │     Patient · Encounter · Observation · MedicationRequest 4종을 "완결로" 매핑
   │     (코드 값은 로컬 코드셋 테이블로 고정, 표준 용어체계 확장 지점만 문서화)
   ├─ REST API      : FHIR 리소스 조회(read/search 최소 프로파일)
   │     레거시 DB를 API에 직접 노출하지 않음 — 변환 계층 경유가 원칙
   ├─ 운영 콘솔      : 배치 상태·실패 재처리 / 장애 대시보드 / 감사 조회(감사자 전용)
   └─ 조회 최적화    : 물리 요약 테이블 + 배치 정기 refresh (최종 일관성 패턴)
        ▼
[Nginx] ─ [운영 콘솔 UI]        [Prometheus → Grafana 대시보드·알림]
```

### 3.2 데이터 모델 — 핵심 결정
- 레거시 테이블: `PATIENT` / `VISIT`(외래·입원) / `LAB_RESULT` / `PRESCRIPTION` — 병원 OCS
  골격의 최소 재현.
- **환자 식별은 불변 내부 PK(patient_id)로 통일**: FHIR 리소스 ID, 감사로그 대상, 배치 upsert
  키가 전부 같은 값을 참조합니다. 화면 표시용 번호는 별도 컬럼으로 분리. 표시용 식별자를
  주기적으로 바꾸는 설계는 과거 감사 기록과의 연결이 끊겨 **금지** — 이 프로젝트에서 가장
  중요한 무결성 원칙입니다.
- 주민등록번호는 어떤 형태로도(해시 포함) 식별자로 쓰지 않습니다.
- FHIR 매핑은 4종을 깊게: 넓고 얕은 매핑보다 "이 리소스는 왜 이렇게 매핑했나"를 설명할 수
  있는 좁고 완결된 매핑이 면접에서 강합니다.

### 3.3 보안·개인정보 설계
- **RBAC 5역할**(의사/간호사/원무/전산관리자/감사자) + 접근정책 테이블(`access_policy_rules`)
  로 "누가 어떤 사유로 무엇을 볼 수 있나"를 데이터로 관리.
- **응급 예외(break-glass)**: 응급 상황은 사유 필수 입력 후 접근을 허용하되, 전용 결과 코드로
  감사 기록 + Grafana 알림 + 사후 감사 대상으로 처리. "막기만 하는 보안"이 아니라 병원 현실을
  아는 설계라는 인상을 줍니다.
- **감사 로그**: 행위자·대상(불변 PK)·행위·목적·마스킹 여부·IP·성공 여부·시각. **조회 쿼리
  원문은 저장하지 않음**(개인정보 문자열이 로그로 새는 경로 차단).
- **비식별·암호화 — 구현 깊이 2단계** (§5 옵션 C):
  - 기본형: 화면 마스킹 + 대량 조회·내보내기 차단 + 전 건 감사 기록
  - 심화형: HMAC-SHA-256 가명화, 민감 필드 AES-256-GCM + 엔벨로프 암호화(마스터 키는 Docker
    secret 주입, 키 회전 절차 문서화), 날짜 이동(date shifting), k-익명성(k=5) 통계,
    대량 복호는 신청→승인→실행 3단계 승인 흐름

### 3.4 운영·배포 설계 — 이 포트폴리오의 차별화 코어
- Docker Compose 단일 노드. 환경변수·시크릿 분리, 재기동 절차 문서화(무중단이 아님을 정직하게
  명시 — 과장하지 않는 것도 설계).
- **산출물 로드맵**:
  - **P0 (필수 6종)**: ① 장애 시나리오 재현·대응 로그북(DB 커넥션 고갈·배치 실패·디스크 임계
    등 4종 내외, Grafana 알림 연동) ② 배치 실패→재처리 runbook ③ 슬로우 쿼리 튜닝 전후
    기록(실행계획 비교 1건 이상) ④ 백업·복구 리허설(복구 소요시간 실측) ⑤ 감사 로그 조회
    화면 ⑥ FHIR 변환 데모
  - **P1**: 요약 테이블 리포팅, 비식별 통계 화면
  - **P2**: Oracle 분기 문서, FHIR 리소스 확장

### 3.5 채용 요건 ↔ 증빙 매핑
| 채용에서 실제로 보는 것 | 이 포트폴리오의 증빙 |
|---|---|
| SQL (Oracle/MySQL 택1) | 튜닝 전후 기록·실행계획 비교, DB 분기 문서 |
| Java 계열 역량 | Spring Boot 서비스 전체 |
| EMR/HIS 운영·유지보수 감각 | 장애 로그북·재처리 runbook·백업 리허설 |
| 최신 트렌드 이해 | FHIR R4 변환 데모, EMR 인증제 요구(접근권한·이력관리) 대응 서술 |
| 개인정보·보안 의식 | RBAC·응급 예외·감사로그·비식별 설계 |

## 4. 선택 옵션 (어느 쪽이든 무방 — 추천 기준만 다름)

| 옵션 | A | B | 추천 기준 |
|---|---|---|---|
| 프론트 | React 18 + TS | Thymeleaf + AdminLTE | 웹 개발 역량까지 어필하려면 A, 백엔드·운영에 시간을 몰려면 B |
| Oracle 분기의 조회 최적화 | Materialized View 사용 | MySQL과 동일하게 요약 테이블 통일 | Oracle 고유 기능 경험을 어필하려면 A, 두 분기 코드 일관성을 원하면 B |
| 보안 구현 깊이 | 기본형(마스킹+차단+감사) | 심화형(암호화·키 관리·승인 흐름까지) | 제작 기간이 짧으면 A로 완성 우선, 보안 직무 가중치가 크면 B |

## 5. 시작 전 확인 목록

- Synthea(합성 데이터 생성기) 산출 형식·라이선스 확인
- EMR 인증제 세부 심사 문항(한국보건의료정보원 공시) 확인 — 접근권한·이력관리 항목을 설계
  서술에 인용하면 어필 강도가 올라감
- Oracle 19c의 Docker 실행 방식(라이선스·이미지)은 분기 구현 전 확인 필요
- 목표 병원 규모(중소 vs 대형)에 따라 DB 분기 우선순위 결정
