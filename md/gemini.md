# Gemini CLI 검증 파이프라인 가이드

> 큰 작업을 step으로 쪼개 진행할 때, **각 step의 완수 여부를 Claude가 self-judge하지 않고
> 외부 에이전트 `gemini`(Google Gemini CLI)에 위임**해서 독립 검증한다.
> 이 문서는 그 호출 방식과 함정(시행착오)을 고정한다. 다음엔 바로 이 패턴을 쓴다.
> gemini 쿼터가 막히면 §0-2(Phase 배칭) → §0-3(Claude subagent 대체 검증) 순으로 내려간다.

---

## 0. 핵심 원칙

- **gemini = 판정자(verifier)**. Claude는 구현하고, "완수했다"는 판정은 gemini가 내린다.
- **step 실행 주체는 기본적으로 subagent다.** 오케스트레이터(메인 세션)는 step 설계·투입·독립 검증만 하고, 각 step의 구현→gemini 검증→커밋 루프 전체는 투입된 subagent가 자기 턴 안에서 완주한다. → §4c
- gemini에는 **명확한 acceptance criteria**(검증 기준)를 주고, 마지막에 `VERDICT: PASS|FAIL`만 받는다.
- gemini는 **읽기 전용 검증**만 하도록 지시한다. 단 `--approval-mode=yolo`로 모든 도구 호출(읽기·쓰기·실행 포함)을 자동 승인시켜 돌리므로, 파일을 건드릴 *가능성*은 여전히 있다 → **실행 전/후 `git status` 비교** 안전망을 둔다.
- ⚠️ **과반응 금지**: 안전망은 *gemini가 이번 step 대상 파일을 의도치 않게 바꿨는지*만 본다. 사용자가 **병행 편집**한 무관한 파일까지 gemini 탓으로 오인해 되돌리거나 사용자에게 캐묻지 않는다. → §4b

### 0-1. gemini를 도장이 아니라 **적대자**로 써라

Claude가 만든 테스트·기준·시나리오는 전부 **Claude의 이해에서 나오므로 Claude의 맹점을 그대로 물려받는다.** "내가 의도한 게 구현됐나?"만 물으면 gemini는 그 맹점을 통과시킨다. 그래서 gemini 프롬프트는 기본이 **적대적**이어야 한다:

1. **완결성 감사를 기준으로 명시**: "X가 존재하나?"가 아니라 "이 열거/커버리지에서 **빠진 케이스를 전부 나열하라**(없으면 '누락 없음' 명시)"를 acceptance criterion으로 넣는다.
2. **입력 오탐 감사**: 판정·필터·가드 코드는 gemini에게 "이 predicate/정규식/부분문자열 매칭에 **정상 입력이 잘못 걸릴 수 있는 경우를 전부 찾아라**(동음이의·부분문자열·문맥 무시)"를 시킨다. Claude가 못 본 것을 gemini는 독립적으로 잡는다(둘이 동시에 같은 실수를 할 확률은 낮다 — 이게 교차검증의 존재 이유다).
3. **diff가 아니라 상호작용 면(surface)을 스코프로**: 기존 코드와 공존하는 기능은 "내 새 파일" 말고 **"이 변경이 함께 도는 전체 계층과 충돌·중복·모순하는지"**를 감사시킨다. 상호작용 버그는 diff 밖에 산다.
4. **닫힌 루프 검증**: 기능이 **내보내는 산출물이 곧 입력이 되는 경우**, 내보낸 모든 산출물을 다시 입력으로 먹여 전 게이트를 통과하는지 테스트한다. 자기모순은 여기서만 잡힌다.

> 초록불은 결승선이 아니라 "더 세게 찔러라"는 신호다. **독립적 적대자(gemini의 적대 감사 + Claude가 저작하지 않은 입력)가 못 깨뜨릴 때까지** 반복한다.

### 0-2. 무료 티어 일일 쿼터 제약 — Phase 단위 검증 배칭

- gemini CLI 무료 티어는 **일일 요청 한도**가 있다(실측: `gemini-3.5-flash` 20회/일, `gemini-3.1-pro`는 사실상 0회). 한도 소진 시 에러는 `TerminalQuotaError: You have exhausted your daily quota`로, §5의 429(분당 레이트리밋)와 달리 **짧은 재시도로는 풀리지 않는다**(일일 리셋 전까지 막힘).
- 이 제약 때문에 step마다 gemini를 호출하는 §4의 기본 루프는, step 수가 많은 계획(예: `docs/planning/PLAN.md`처럼 수십 step)에서는 하루 안에 끝나지 않는다.
- **완화책(2026-07-17, 사용자 승인 — 무료 쿼터로 운영하는 동안 기본값)**: step마다 gemini를 부르지 않고, **Phase(여러 step 묶음)가 끝나는 시점에 그 Phase의 누적 diff를 gemini에 한 번만** 검증받는다.
  - **커밋은 여전히 step 단위로 쪼갠다** — "한 step = 한 커밋" 원칙(§4 진행 정책)은 그대로 유지한다. 다만 그 시점엔 gemini VERDICT가 없으므로, 커밋 메시지에 "gemini 검증은 Phase 종료 시점 일괄 예정"이라고 반드시 남긴다.
  - Phase의 마지막 step까지 구현·로컬 검증(빌드/테스트)·커밋이 끝나면, 그 Phase에 속한 전체 커밋의 누적 diff를 acceptance criteria로 묶어 gemini를 한 번 호출한다.
  - `VERDICT: PASS` → Phase 전체를 완료로 간주한다. `VERDICT: FAIL` → 어느 step의 어느 산출물이 문제인지 특정해 해당 step만 수정 후 재검증한다(Phase 전체를 되돌리지 않는다).
  - 이 배칭은 **쿼터가 실제로 부족할 때 쓰는 완화책**이다 — 쿼터 여유가 있는 세션(예: 과금되는 키)에서는 §4의 step당 검증이 기본값이다.

### 0-3. gemini가 완전히 막혔을 때 — Claude subagent 대체 검증

§0-2의 Phase 배칭으로도 그날 남은 호출을 다 썼거나(같은 Phase 검증 중에 또 `TerminalQuotaError`), 애초에 재시도할 여지가 없이 완전 소진됐다면 gemini를 더 부를 수 없다. 이때도 **검증 자체를 생략하지 않는다** — 무기한 대기하는 대신 **별도의 독립 Claude subagent를 검증자로 띄운다.**

- **독립성이 핵심**: 검증 subagent는 **구현을 진행한 subagent와 별개의 새 Agent 호출**이어야 한다(같은 turn·같은 대화 맥락을 이어받으면 안 됨). 구현자의 설명이나 "다 됐다"는 자기보고를 넘기지 말고, **diff와 acceptance criteria만** 건네 처음부터 스스로 판단하게 한다 — 그래야 §0-1의 "적대자" 취지(구현자의 맹점을 그대로 물려받지 않는 것)가 최소한이라도 유지된다.
- **같은 모델이 같은 모델을 검증하는 것이라 gemini의 교차 모델 검증보다 약하다**는 걸 인지하고 쓴다. 그래서 검증 subagent 프롬프트는 §3 템플릿보다 한층 더 적대적으로 짜라: "구현자가 스스로 통과라고 보고했더라도 그대로 믿지 말고, 각 acceptance criterion을 네가 직접 커맨드를 실행하거나 파일을 읽어서 재확인하라"를 명시한다.
- 호출 방법: Agent tool로 **새 subagent**를 투입하고, 프롬프트에 다음을 포함한다:
  1. [검증 대상] 대상 파일/커밋 범위(`git diff <시작>..<끝>` 또는 대상 pathspec) — 구현자의 서술이 아니라 이 범위 자체를 근거로 삼으라고 명시.
  2. [acceptance criteria] §3과 동일한 형식(기계적으로 확인 가능한 조건들).
  3. 출력 규약은 gemini와 **동일하게 유지**: "읽기 전용 검증이다. 파일을 수정하지 마라. 기준마다 네가 직접 실행/확인한 근거를 한 줄씩 적고, 마지막 줄에 정확히 'VERDICT: PASS' 또는 'VERDICT: FAIL (사유)'만 출력하라." — 오케스트레이터의 판정 로직이 검증자가 gemini든 Claude subagent든 동일하게 동작하게 하기 위함이다.
- `VERDICT: PASS`/`FAIL` 이후 절차(§4 4~5단계 — 커밋·재시도·중단 기준)는 검증자가 무엇이든 **동일하게 적용**한다.
- 이 경로를 쓴 step/Phase는 커밋 메시지에 **"gemini 대신 Claude subagent(독립 검증)로 VERDICT 획득"**을 명시한다 — 나중에 git log만 보고 어떤 검증 경로였는지 알 수 있어야 한다.
- **우선순위**: gemini(정상 쿼터, §4) > gemini(Phase 배칭, §0-2) > Claude subagent 독립 검증(§0-3). 상위 경로가 가능하면 항상 먼저 시도하고, 정말 막혔을 때만 이 경로로 내려온다.

## 1. 사전 조건

```bash
command -v gemini && gemini --version
```

설치 경로는 환경마다 다르므로 `command -v gemini`로 확인한다. (npm 설치 시 `@google/gemini-cli` 패키지, 바이너리명은 `gemini`.)

인증은 별도로 `gemini` 최초 실행 시(또는 `GEMINI_API_KEY` 환경변수) 끝나 있어야 한다 — 검증 호출 도중 로그인 흐름이 끼면 비대화형 실행이 멈춘다.

## 2. 표준 호출 (copy-paste)

```bash
gemini --approval-mode=yolo --skip-trust \
  -p "<검증 프롬프트 — 아래 템플릿 참고>" < /dev/null
```

**플래그 의미**
| 플래그 | 이유 |
|--------|------|
| `-p` / `--prompt` | 프롬프트를 즉시 실행하고 결과를 출력한 뒤 종료(비대화형 강제). TUI 안 띄움 |
| `--approval-mode=yolo` | 모든 도구 호출(읽기/쓰기/실행)을 자동 승인. 기본값(`default`)으로 두면 각 도구 호출마다 승인 대기 상태로 멈춘다 — codex의 `--dangerously-bypass-approvals-and-sandbox`에 대응 |
| `--skip-trust` | 처음 접근하는 폴더의 "이 디렉터리를 신뢰합니까?" 확인을 건너뜀. 없으면 비대화형 실행이 트러스트 프롬프트에서 멈출 수 있음 |
| `< /dev/null` | **stdin을 닫는다.** `-p`는 stdin이 열려 있으면 입력 종료를 기다리며 대기할 수 있음 — 안 닫으면 무한 대기 가능 |

`--sandbox`(`-s`)는 **기본값이 꺼짐(false)**이므로 codex처럼 별도로 끌 필요가 없다. 오히려 Docker/Podman이 없는 환경에서 `--sandbox`를 켜면 컨테이너 실행에 실패할 수 있으므로 **이 플래그는 아예 주지 않는다.**

필요 시 `--allowed-mcp-server-names <name1>,<name2>` 로 이번 검증에 필요한 MCP 서버만 화이트리스트할 수 있다(전역 `~/.gemini/settings.json`은 건드리지 않음). 생략하면 설정된 MCP 서버가 모두 붙어 로그만 지저분해질 수 있다.

**모델**: `-m`/`--model`을 주지 않으면 기본값 `auto`가 쓰인다(`pro`/`flash`/`flash-lite` 별칭 또는 `gemini-2.5-pro` 같은 구체 모델명도 가능). 계정에서 쓸 수 있는 최상위 모델을 명시적으로 고정해두는 것을 권장한다(`-m pro` 등).

실행 **전후로 비교** (전체 클린 여부가 아니라 *델타*만 본다):
```bash
git status --porcelain > /tmp/gemini_pre.txt        # gemini 실행 전 baseline 스냅샷
gemini --approval-mode=yolo --skip-trust -p "..." < /dev/null   # 검증 실행
git status --porcelain | diff /tmp/gemini_pre.txt -  # 델타 = gemini 실행 중 생긴 변경 후보
```
델타가 **이번 step 대상 파일 밖**이면 gemini가 아니라 사용자 병행 작업일 공산이 크다 → §4b 판단.

## 3. 검증 프롬프트 템플릿

```
읽기 전용 검증 작업이다. 어떤 파일도 수정하지 마라.

[목표] <이 step이 달성하려던 것 한 줄>

[검증 기준] 아래를 각각 확인하라:
1. <구체·기계적으로 확인 가능한 조건 1>
2. <조건 2 — 예: 특정 빌드/테스트 명령이 통과>
3. <조건 3 — 예: 특정 함수/엔드포인트/스키마가 존재하고 ~하게 동작>

[출력] 각 기준의 통과 여부를 한 줄씩 적고,
마지막 줄에 정확히 'VERDICT: PASS' 또는 'VERDICT: FAIL (사유)' 만 출력하라.
```

원칙:
- 기준은 **기계적으로 확인 가능**해야 한다(파일/함수/스키마 존재, 빌드·테스트 통과, 특정 문자열 부재 등). "예쁜가?" 같은 주관 기준 금지.
- 빌드/테스트 실행을 시키면 gemini가 직접 돌려서(`--approval-mode=yolo`이므로 승인 없이 실행 가능) 결과로 판정한다(읽기만으로 부족할 때).
- "수정 금지" 지시는 프롬프트 텍스트로만 강제된다(OS 샌드박스가 막아주는 게 아니다) — §2의 `git status` 안전망이 실질적 방어선이다.

## 4. step 진행 루프

> 이 루프의 실행 주체는 기본적으로 **step 담당 subagent**다(§4c). 오케스트레이터가 직접 돌리는 건 작은 단발 작업일 때뿐이다. 아래 "Claude"는 그 step을 실행 중인 에이전트(대개 subagent)를 뜻한다.

1. Claude가 step 구현 → 자체 빌드로 1차 확인.
2. gemini 실행 전 `git status` baseline 스냅샷(§2).
3. 해당 step의 acceptance criteria로 **gemini 검증 호출**(§2).
4. `VERDICT: PASS` + (델타에 **step 대상 파일**에 대한 gemini의 의도치 않은 수정 없음):
   - a. **step 대상 파일만 명시적으로** `git add <files>` 후 커밋. 메시지에 step 번호·목표 명시.
     무관한 사용자 변경(병행 작업)은 **절대 staging 금지**.
   - b. **곧바로 다음 step으로 진행한다. "계속할까요?"라고 묻지 않는다.** (이미 전체 진행을 위임받았다는 전제)
5. `VERDICT: FAIL` → 사유를 보고 수정 후 3번 재실행. (Claude가 임의로 "됐다" 하지 않는다.)

### 진행 정책 (커밋·자동 진행)

> 무료 티어 쿼터 소진 상황에서는 이 루프 대신 **§0-2(Phase 단위 검증 배칭)**를 따른다 — step별 커밋 원칙은 동일하지만 gemini 호출을 Phase 끝으로 미룬다.

- **step별 커밋**: PASS 받은 step은 그 즉시 대상 파일만 커밋한다. 한 step = 한 커밋(원칙).
- **묻지 않고 계속**: PASS면 사용자 확인 없이 다음 step을 바로 시작한다. 진행 자체를 멈추고 묻는 건 아래 *진짜 멈춰야 할 때*로 한정한다.
- **push**: 매 step push하지 않는다. 기능이 일관된 마일스톤에 도달했거나 사용자가 요청할 때 push. (미완 기능을 공유 브랜치에 매 step 흘리지 않기 위함)
- **진짜 멈춰야 할 때만 사용자에게 묻는다**:
  1) 설계가 갈리는 진짜 모호함(코드/맥락으로 못 정함), 2) 같은 step이 FAIL 반복(2~3회)으로 막힘,
  3) 되돌리기 어렵거나 외부로 나가는 작업(force push·삭제·배포 등). 그 외에는 멈추지 않는다.

---

## 4b. 안전망 운용 — 과반응 금지 (중요)

gemini 실행 후 `git status`에 변경이 보여도 **전부 gemini 탓이 아니다.** 사용자는 그 사이
다른 파일을 병행 편집할 수 있다. 다음 절차로 **귀속(attribution)** 부터 판단한다:

1. **델타가 step 대상 파일인가?** (이번에 내가 만지는 소스 + gemini가 빌드/검사한 파일)
   - 예 → gemini가 건드렸을 수 있음. 내용 확인 후 필요시 되돌림.
   - 아니오(무관한 문서·다른 기능·사용자의 알려진 WIP) → **gemini 아님.** 그대로 둔다. 되돌리거나 캐묻지 않는다.
2. 애매하면 **사용자에게 단정 짓지 말고** "이건 의도한 변경인가요?"로 가볍게 확인. *gemini가 망가뜨렸다고 단정 보고 금지.*
3. 커밋 시에는 어차피 **step 대상 파일만 명시적으로 `git add`** 하므로, 무관한 변경은 자연히 섞이지 않는다.

> codex 파이프라인에서도, 검증 후 다수의 파일 변경이 보였지만 알고 보니 사용자가 별도로 진행한 무관한 작업(다른 기능/문서 정리)이었던 사례가 있었다. step 대상 파일이 아니면 스코프 밖 → gemini 무관. 이런 걸 gemini 탓으로 오인하지 말 것. `--approval-mode=yolo`는 승인 절차를 생략할 뿐 gemini의 판단력 자체를 낮추는 건 아니므로, 지시받지 않은 파일을 먼저 의심하기보다 델타 귀속부터 확인한다.

## 4c. subagent 위임 모드 — step 실행의 기본형

step 작업은 오케스트레이터(메인 세션)가 직접 하지 않고 **step(또는 작업 묶음) 담당 subagent에게 위임**한다. subagent가 구현부터 gemini 검증·커밋까지 §4 루프 전체를 자기 턴 안에서 완주하고, 오케스트레이터는 계획·투입·독립 검증·다음 step 투입만 맡는다.

### 3계층 역할 분리

| 계층 | 하는 일 | 하지 않는 일 |
|------|---------|--------------|
| 오케스트레이터(메인) | step 분할, acceptance criteria 저작, subagent 투입, 보고의 **git 독립 검증**, 다음 step 투입 | 직접 구현 (컨텍스트를 계획·검증에 아낀다) |
| subagent | step 구현 → 빌드/테스트 → gemini 호출 → FAIL 수정·재검증 → PASS 시 명시 pathspec 커밋 → 결과 보고 | 판정(self-judge), 스코프 밖 파일 접촉, 사용자에게 직접 질문 |
| gemini | `VERDICT: PASS\|FAIL` 판정 | 구현·수정 |

핵심: **판정 권한은 여전히 gemini에만 있다.** subagent도 Claude이므로 self-judge 금지가 그대로 적용된다. subagent는 gemini의 VERDICT **원문(마지막 줄)을 보고에 포함**해야 하며, "gemini 검증 통과했다"는 요약만으로는 검증된 것으로 인정하지 않는다.

### subagent 투입 프롬프트 템플릿 (필수 요소 전부 포함)

```
[step 목표] <한 줄>
[대상 파일] <명시 — 이 밖의 파일은 접촉 금지>
[acceptance criteria] <기계적으로 확인 가능한 조건들 — gemini 프롬프트에 그대로 쓸 것>

[필수 규칙]
1. 이 문서(gemini 가이드)를 먼저 읽고 §2 호출 형식·§3 프롬프트 템플릿·§4 루프를 그대로 따르라.
2. gemini·빌드·테스트는 전부 **포그라운드로 실행**하라. 백그라운드 실행 후 알림 대기 금지.
   테스트는 비대화형 1회 실행 모드로 대상 범위만 좁혀 돌려라.
3. gemini에 판정 기준을 `git diff --cached --name-only`(스테이징된 것)로 선고지하라.
   워킹트리의 병행 더티 파일은 판정 대상이 아니다.
4. 줄바꿈 자동변환 환경(core.autocrlf 등)이라면 바이트/내용 비교는 저장소 blob 기준으로 하라
   (워킹트리 개행 대조는 오탐).
5. PASS 후 커밋은 **대상 파일만 명시 pathspec으로** `git add`. 그 외 파일 staging 절대 금지.
6. FAIL이면 수정 후 재검증. 같은 step FAIL 2~3회 반복이거나 설계가 갈리는 모호함이면
   **더 진행하지 말고 그 상태 그대로 보고하라** (사용자에게 묻지 말 것 — 판단은 오케스트레이터가 한다).

[보고 형식] step별로: 커밋 해시 / gemini VERDICT 원문 / FAIL이 있었다면 사유·수정 내역 / 이월 발견사항.
```

프롬프트에 왜 저 항목들이 필수인가 (codex 파이프라인에서 실제 겪은 사고 유형 — gemini에도 동일하게 적용):

- **포그라운드 강제(2)**: subagent가 gemini·테스트를 백그라운드로 돌리고 알림을 기다리다 턴을 끝내는 패턴이 반복적으로 관찰됐다. 프롬프트에 명시하면 무정지 완주한다.
- **`git diff --cached` 선고지(3)**: 사용자 병행 편집 더티 파일을 검증 에이전트가 "변경 범위"로 오판해 FAIL하는 사례가 있었다. §4b 과반응 문제는 gemini 쪽에서도 난다.
- **blob 기준 비교(4)**: 줄바꿈 자동변환 환경에서 워킹트리 개행 vs 저장소 blob을 비교하는 바이트 동일성 검증이 헛 FAIL을 낸 사례가 있었다.

### 순차 투입 — step subagent 병렬 금지

step subagent는 **한 번에 하나만** 투입한다. gemini의 git-status 안전망(§2)과 명시 pathspec 커밋 위생이 전부 워킹트리 상태를 전제하므로, 같은 저장소에 subagent를 병렬로 풀면 서로의 델타를 오염시켜 안전망 자체가 무의미해진다. (사용자의 병행 세션은 §4b대로 귀속 판단으로 흡수하지만, 우리 스스로 병렬을 만드는 것은 금지.)

### 오케스트레이터의 독립 검증 — 자기보고를 믿지 마라

subagent 보고를 받으면 **git으로 대조한 뒤에만** 그 step을 완료 처리한다:

1. `git log --oneline <투입 전 HEAD>..HEAD` — 커밋 수·메시지가 보고와 일치하는가. (자기보고 커밋 수가 실제와 달랐던 사례가 있다 — 수치는 항상 git이 정본.)
2. `git show --stat <해시>` — 각 커밋에 스코프 밖 파일이 섞이지 않았는가.
3. 보고에 step별 gemini VERDICT **원문**이 있는가. 없으면 미검증으로 간주하고 오케스트레이터가 직접 §2로 gemini를 재실행해 판정을 받는다.
4. 빌드/타입체크 게이트를 오케스트레이터가 한 번 더 돌린다 (번들러 빌드가 타입체크를 생략하는 프로젝트라면 타입체커 직접 실행 필수).

### subagent가 도중에 죽었을 때

subagent가 최종 보고 전에 종료(크레딧 소진·프로세스 사망)돼도 **커밋이 진실**이다. `git log`로 어디까지 PASS·커밋됐는지 재구성하고, 미완 부분만 acceptance criteria를 조정해 새 subagent를 재투입한다. VERDICT 원문이 유실됐더라도 커밋 내용·빌드는 사후 git/실행 검증으로 복원할 수 있다.

## 5. 함정 & 트러블슈팅

| 증상 | 원인 | 대응 |
|------|------|------|
| stdin 대기 메시지 후 무한 대기 | `-p` 사용 시 stdin 미닫힘 | `< /dev/null` 추가 |
| "이 폴더를 신뢰합니까?" 같은 확인 대기에서 멈춤 | 폴더 트러스트 확인이 비대화형 실행을 막음 | `--skip-trust` 추가 |
| 도구 호출마다 승인 대기로 멈춤 | `--approval-mode`가 기본값(`default`)이라 매 호출마다 사용자 승인을 기다림 | `--approval-mode=yolo` 지정 |
| 샌드박스(Docker/Podman) 관련 실행 실패 | `--sandbox`(`-s`)를 켰는데 컨테이너 런타임이 없거나 설정이 안 됨 | `--sandbox` 플래그를 아예 주지 않는다 (기본값 false로 충분) |
| MCP 관련 transport/연결 오류 로그 | `~/.gemini/settings.json`에 등록된 MCP 서버가 안 떠 있음 | 로그를 깔끔히 하려면 `--allowed-mcp-server-names`로 필요한 서버만 화이트리스트 |
| `--yolo`(`-y`) 사용 시 deprecation 경고 | `--yolo`는 구식 플래그 | `--approval-mode=yolo`로 교체 |
| 토큰 사용량 비정상 폭증 | 승인 대기·트러스트 대기에서 재시도 thrash | 위 플래그 교정으로 해결됨 |

> 정리: **`--sandbox`는 건드리지 않는다(기본 꺼짐).** "수정 금지" 프롬프트 지시 + 실행 후 `git status` 대조가 실질 안전망이다.
> MCP 노이즈는 결과에 영향이 없다 — 필요 서버만 화이트리스트하거나 그냥 무시하면 된다.

```bash
gemini --approval-mode=yolo --skip-trust \
  -p "읽기 전용 검증. 수정 금지. <경로>가 존재하는가?
      마지막 줄에 'VERDICT: <PRESENT|ABSENT>' 만 출력하라." < /dev/null
```
