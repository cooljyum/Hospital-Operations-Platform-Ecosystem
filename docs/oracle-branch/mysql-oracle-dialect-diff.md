# MySQL 8.x ↔ Oracle 19c 문법 차이표

이 프로젝트의 정본 스키마(MySQL 8.x, `app/src/main/resources/db/migration/V1~V16`)를
Oracle 방언으로 옮기며 실제로 부딪힌 차이만 정리한다. 일반적인 SQL 표준 차이 전체를
나열하지 않고, **이 스키마를 번역하면서 실제로 고쳐야 했던 지점**만 다룬다 —
`schema-oracle.sql`/`query-optimization-mv.sql`의 주석과 1:1로 대응된다.

| 항목 | MySQL 8.x | Oracle 19c | 이 프로젝트에서 실제로 부딪힌 지점 |
|---|---|---|---|
| 자동 증가 PK | `BIGINT AUTO_INCREMENT` | `NUMBER(19) GENERATED BY DEFAULT AS IDENTITY` | 전 테이블의 대리키(`patient_id`, `visit_id` 등). Oracle 12c+ 네이티브 identity 컬럼 사용(구버전처럼 SEQUENCE+트리거를 손으로 안 만들어도 됨). |
| 가변 문자열 | `VARCHAR(n)` | `VARCHAR2(n)` | 전 테이블. Oracle에 `VARCHAR`도 문법상 존재하지만 향후 의미가 바뀔 수 있어 공식적으로 `VARCHAR2` 사용이 표준. |
| 대용량 텍스트 | `TEXT` / `LONGTEXT` | `CLOB` | `FHIR_RESOURCE_CACHE.resource_json`(V5) — FHIR 리소스 JSON 전문 저장 컬럼. |
| 날짜/시각 | `DATE` / `DATETIME` | `DATE`(시각 없음 컬럼) / `TIMESTAMP` | `birth_date`/`death_date`는 `DATE`로 남기고, `started_at`/`occurred_at` 등 시각까지 필요한 컬럼은 `TIMESTAMP`로. |
| 현재 시각 기본값 | `DEFAULT CURRENT_TIMESTAMP` | `DEFAULT SYSTIMESTAMP` | 전 테이블의 `created_at`/`occurred_at` 등. |
| 갱신 시각 자동화 | `DATETIME ... ON UPDATE CURRENT_TIMESTAMP` | 직접 대응 문법 없음 → `BEFORE UPDATE` 행 트리거로 구현 | `PATIENT.updated_at` 등 4개 테이블. Oracle은 컬럼 자동 갱신을 선언적으로 못 하고 트리거가 필수라는 점이 가장 눈에 띄는 차이(`schema-oracle.sql`의 `trg_*_updated_at` 4~5개). |
| 불리언 컬럼 | `BOOLEAN`(내부적으로 `TINYINT(1)`) | 네이티브 없음(23c부터 지원, **19c는 미지원**) → `NUMBER(1)` + `CHECK (col IN (0,1))` | `APP_USER.enabled`, `AUDIT_LOG.masked`/`success`, `ACCESS_POLICY_RULES.allowed`, `PATIENT_DISPLAY_ID.is_active` 등 6곳. |
| 생성 컬럼(계산 컬럼) 저장 방식 | `GENERATED ... STORED`(디스크에 실제 저장) | `STORED` 미지원, `GENERATED ALWAYS AS (...) VIRTUAL`만 지원(조회 시 계산, 인덱스는 가능) | `LAB_RESULT.result_value_key`, `PRESCRIPTION.stopped_at_key`(V3) — NULL 유니크 제약 우회용 센티널 생성 컬럼. 기능은 동등(유니크 제약 가능)하나 저장 방식이 다름. |
| 인덱스 소속 개념 | 인덱스가 테이블에 종속(`ALTER TABLE t DROP INDEX idx`, `RENAME INDEX old TO new`) | 인덱스가 스키마 레벨 독립 오브젝트(`DROP INDEX idx`, `ALTER INDEX old RENAME TO new` — 테이블명 불필요) | V3의 "새 인덱스 추가 → 기존 DROP → RENAME" 3단계 절차에서 문법이 달라짐(`schema-oracle.sql` V3 섹션 주석 참고). |
| 다중 행 INSERT | `INSERT INTO t (...) VALUES (...), (...), (...)` 한 문장 | 미지원 — 문장당 1행만, 여러 행은 별도 INSERT 또는 `INSERT ALL ... SELECT * FROM DUAL` | V6 `CODE_SET` 시드 데이터(56행) — 개별 `INSERT` 문 56개로 번역. |
| 무조건 삽입/멱등 시드 | `INSERT ... SELECT ... WHERE NOT EXISTS (SELECT * FROM t)` | 동일 패턴 가능(`FROM DUAL` 활용)하나 이 프로젝트에서는 신규 스키마라 불필요(Spring Batch 카운터 테이블 자체를 안 씀 — 아래 항목 참고) | V5의 `BATCH_*_SEQ` 1행 카운터 테이블 3개. |
| Spring Batch 메타데이터 스키마 | `spring-batch-core` jar의 `schema-mysql.sql`(카운터 테이블 3개로 시퀀스 에뮬레이션) | 같은 jar의 `schema-oracle.sql`(네이티브 `CREATE SEQUENCE` 3개 사용, 카운터 테이블 없음) | V5 전체. **손으로 번역하지 않고 공식 파일을 그대로 채택**하는 것이 정답 — 구조 자체가 다르다(테이블 3개 vs 시퀀스 3개). |
| 엔진/문자셋 절 | `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci` | 대응 개념 없음(문자셋은 DB 생성 시 `AL32UTF8` 지정, 스토리지 엔진 선택 개념 자체가 없음) | 전 `CREATE TABLE`에서 제거. |
| 물리 요약 테이블 vs MV | 요약 테이블 + Spring Batch tasklet이 `DELETE` 후 재집계 `INSERT`(V13, `SummaryRefreshTasklet`) | 네이티브 `MATERIALIZED VIEW ... REFRESH COMPLETE ON DEMAND` + `DBMS_MVIEW.REFRESH('MV명', 'C')` | 조회 최적화 오브젝트 자체(`query-optimization-mv.sql`). Oracle 분기의 의도적 선택 — 근거는 `README.md` 참고. |
| 실행계획 확인 | `EXPLAIN` / `EXPLAIN ANALYZE` | `EXPLAIN PLAN FOR ...` + `SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(...))`(2문장 필요) | `query-optimization-mv.sql` 마지막 섹션. |

## 번역하지 않고 그대로 둔 것

- SQL 자체 문법(`SELECT`/`JOIN`/`GROUP BY`/`WHERE` 등 표준 DML)은 두 DB가 사실상
  동일해 변경하지 않았다. `SummaryRefreshTasklet`의 집계 쿼리 구조를 MV 정의에
  그대로 재사용할 수 있었던 이유이기도 하다.
- 외래키(`FOREIGN KEY ... REFERENCES`), `UNIQUE`, `CHECK` 제약 문법은 두 DB가 동일하다.
- `CREATE INDEX ON table (cols)` 기본 문법은 동일하다(인덱스가 스키마 레벨 오브젝트라는
  점만 다르고, 생성 문법 자체는 같다).
