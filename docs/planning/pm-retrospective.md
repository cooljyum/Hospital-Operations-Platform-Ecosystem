## 1. 프로젝트 목표

**"Hospital FHIR Ops Lab"** — 병원 전산 관리직(EMR/HIS 운영·유지보수) 채용 지원용 1인 개발
포트폴리오. 합성 병원 데이터를 FHIR R4로 연계하는 미니 시스템을 만들되, **핵심 산출물은 기능이
아니라 "운영 증빙"**이다: 실제로 장애를 재현·대응한 로그북, 배치 실패→재처리 runbook, 슬로우
쿼리 튜닝 전후 기록, 백업·복구 리허설(복구 소요시간 실측), 감사 로그 조회 화면 시연, FHIR 변환
데모. "개발을 해봤다"가 아니라 "시스템을 운영해 봤다"를 증명하는 것이 목표다
(`docs/planning/deliverable.md` §1).

실환자 데이터는 전혀 사용하지 않는다 — 모든 데이터는 Synthea 합성 환자 생성기 산출물이다.

**최종 상태(2026-07-24 기준): 목표 달성됨.** Phase 0~10 전체, deliverable.md가 정의한 P0(필수
6종)·P1·P2 산출물 전부 완료. 완료 근거는 §5의 개별 커밋과, 최초 작성 기준점 `8fb381a`까지의
49개 이력 스냅샷에 기록돼 있다(최신 전체 수는 §0의 명령으로 재확인).

### Milestone 4 — Phase 4: 심화형 보안·비식별

> 5개 Task 전부 "고위험 step"으로 분류(codex.md §3b 기준: 보안·암호화 카테고리) — 각각 별도
> 적대적 검증이 요구되는 영역.

**Task 4.1 — HMAC-SHA-256 가명화**
- 목적: 표시·외부 노출용으로는 결정론적 가명을 쓰되, 내부 PK는 절대 노출하지 않음
- 구현 내용: `Pseudonymizer`
- 완료 기준: 동일 입력 → 동일 해시(결정론적), 원본 PK 미노출
- 예상 난이도: 중
- 선행 작업: 1.1
- 위험 요소: HMAC 키 관리(키 유출 시 가명 역추적 위험 — 무작위 대입으로 원본 식별자 후보를
  해시해 대조하는 공격에 취약할 수 있음, 특히 식별자 공간이 좁을 때)
- 실제 결과: PASS, `53c42bd`(2026-07-19)

**Task 4.2 — AES-256-GCM 엔벨로프 암호화 + 키 회전 runbook**
- 목적: 민감 필드를 실제로 암호화하고, 키 유출/교체 시 전체 재암호화 없이 대응 가능하게
- 구현 내용: `EnvelopeCrypto`(레코드별 무작위 DEK → KEK로 래핑), `docs/runbooks/key-rotation.md`
- 완료 기준: 암복호화 라운드트립 테스트 통과, KEK 없이는 기동 실패(fail-fast), runbook에 회전 절차 명시
- 예상 난이도: 상(엔벨로프 암호화 설계 자체가 정교함 — DEK/KEK 이중 구조, IV 관리, 실패 모드 설계)
- 선행 작업: 4.1
- 위험 요소: **이 설계 결정(KEK 없으면 기동 자체를 막는 fail-fast)이 이후 M11에서 실제
  운영상의 마찰을 일으켰다** — `docker-compose.yml`이 `ENVELOPE_KEK`를 배선하지 않아 Docker
  경로 전체가 기동 불가 상태로 5일간(2026-07-19~2026-07-23) 방치됨. 교훈: "보안을 위해 의도적으로
  빡빡하게 설계한 fail-fast"는 그 자체로는 옳은 결정이지만, **모든 배포 경로(로컬/Docker)에
  그 요구사항이 빠짐없이 전파됐는지 별도로 검증해야 한다** — 코드 검증만으로는 배포 설정 누락을
  못 잡는다
- 실제 결과: PASS, `9abfafe`(2026-07-19). 배포 경로 배선 누락은 M11(`25bc667`, 2026-07-23)에서 해소

## 8. 프로젝트 규칙

이 프로젝트가 실제로 지켰던(그리고 앞으로도 지켜야 할) 규칙 — 사용자가 제시한 프레임워크의
"프로젝트 규칙" 항목을 이 프로젝트의 실제 정책(`CLAUDE.md`, `docs/agents/codex.md`)과 결합해
재정리했다.

- **절대 큰 작업을 한 번에 수행하지 않는다.** → 이 프로젝트는 35개 Task(Phase 0~10) + 4개
  사후 정비 Task로 쪼개 진행했다(§5).
- **항상 가장 작은 작업 단위부터 수행한다.** → Task 하나 = 커밋 하나 원칙(대부분 지켜짐, 예외는
  §5에서 "보완"으로 표기된 fixup 커밋들).
- **하나의 Task가 끝날 때마다 검증한다.** → `docs/agents/codex.md`(과거엔 `gemini.md`) 루프:
  정찰→지시→구현→Claude 판정→(FAIL 시)수정, PASS 전까지 완료로 보고하지 않는다. 고위험 step은
  여기에 별도 Codex 검증 세션의 `VERDICT: PASS`까지 요구한다.
- **문제가 발생하면 원인을 분석한 뒤 수정 계획을 먼저 작성한다.** → Task 11.3(Docker 버그)이
  대표 사례: 진단(11.2)과 수정(11.3)을 별도 세션으로 분리해 진행.
- **추측으로 구현하지 않는다.** → 모든 P0/P1/P2 산출물은 실제 명령 실행 결과(raw 로그·쿼리
  출력·EXPLAIN PLAN·스크린샷)를 근거로 작성 — "실측" 원칙이 문서 전반에 명시적으로 반복됨.
- **구현 전 반드시 설계를 먼저 한다.** → `deliverable.md`(제안서) → `final_summary.md`(합의) →
  `PLAN.md`(step 단위 계획) 순서로 설계 문서가 구현보다 먼저 존재했다.
- **기존 코드 스타일을 유지한다.** → 신규 화면(Task 9.1/9.2)이 기존 화면(Task 5.2)의 컨트롤러·
  템플릿·RBAC 패턴을 그대로 재사용, FHIR 5번째 리소스(Task 10.2)도 기존 4종의 매퍼/Tasklet
  패턴을 그대로 재사용.
- **유지보수성과 확장성을 우선한다.** → RBAC을 하드코딩 대신 `ACCESS_POLICY_RULES` 테이블로,
  코드셋을 하드코딩 대신 `CODE_SET` 테이블로, 배치 동기화 패턴을 Tasklet 단위로 반복 가능하게
  설계(4종 FHIR 매핑 후 5번째도 동일 패턴으로 확장 성공).
- **모든 결정에는 이유를 작성한다.** → 프론트엔드 스택(Thymeleaf), 보안 심화형, Oracle MV
  여부 등 모든 기로에서 Gemini/Codex CLI 자문 근거나 사용자 결정 근거를 커밋 메시지·문서에 기록.
- **(이 프로젝트에서 추가로 지킨 규칙) 정직한 고지.** → "미검증"·"과장 아님"을 명시적으로
  적어두는 관례(`docker/README.md`, `docs/oracle-branch/README.md`의 23ai 고지 등) — 완료
  기준을 슬쩍 낮춰서 "완료"로 포장하지 않는다.

  종료 시 원상복구를 완료 기준의 일부로 취급하고, row count 재대조로 실제 확인한다.
