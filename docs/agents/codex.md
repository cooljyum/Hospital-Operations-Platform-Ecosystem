\# Codex 검증 파이프라인 가이드



> 큰 작업을 step으로 쪼개 진행할 때, \*\*각 step의 완수 여부를 Claude가 self-judge하지 않고

> 외부 에이전트 `codex`(OpenAI Codex CLI)에 위임\*\*해서 독립 검증한다.

> 이 문서는 그 호출 방식과 함정(시행착오)을 고정한다. 다음엔 바로 이 패턴을 쓴다.



\---



\## 0. 핵심 원칙



\- \*\*codex = 판정자(verifier)\*\*. Claude는 구현하고, "완수했다"는 판정은 codex가 내린다.

\- \*\*step 실행 주체는 기본적으로 subagent다.\*\* 오케스트레이터(메인 세션)는 step 설계·투입·독립 검증만 하고, 각 step의 구현→codex 검증→커밋 루프 전체는 투입된 subagent가 자기 턴 안에서 완주한다. → §4c

\- codex에는 \*\*명확한 acceptance criteria\*\*(검증 기준)를 주고, 마지막에 `VERDICT: PASS|FAIL`만 받는다.

\- codex는 \*\*읽기 전용 검증\*\*만 하도록 지시한다. 단 OS 샌드박스를 끄고 돌릴 수도 있으므로 파일을 건드릴 \*가능성\*은 있다 → \*\*실행 전/후 `git status` 비교\*\* 안전망을 둔다.

\- ⚠️ \*\*과반응 금지\*\*: 안전망은 \*codex가 이번 step 대상 파일을 의도치 않게 바꿨는지\*만 본다. 사용자가 \*\*병행 편집\*\*한 무관한 파일까지 codex 탓으로 오인해 되돌리거나 사용자에게 캐묻지 않는다. → §4b



\### 0-1. codex를 도장이 아니라 \*\*적대자\*\*로 써라



Claude가 만든 테스트·기준·시나리오는 전부 \*\*Claude의 이해에서 나오므로 Claude의 맹점을 그대로 물려받는다.\*\* "내가 의도한 게 구현됐나?"만 물으면 codex는 그 맹점을 통과시킨다. 그래서 codex 프롬프트는 기본이 \*\*적대적\*\*이어야 한다:



1\. \*\*완결성 감사를 기준으로 명시\*\*: "X가 존재하나?"가 아니라 "이 열거/커버리지에서 \*\*빠진 케이스를 전부 나열하라\*\*(없으면 '누락 없음' 명시)"를 acceptance criterion으로 넣는다.

2\. \*\*입력 오탐 감사\*\*: 판정·필터·가드 코드는 codex에게 "이 predicate/정규식/부분문자열 매칭에 \*\*정상 입력이 잘못 걸릴 수 있는 경우를 전부 찾아라\*\*(동음이의·부분문자열·문맥 무시)"를 시킨다. Claude가 못 본 것을 codex는 독립적으로 잡는다(둘이 동시에 같은 실수를 할 확률은 낮다 — 이게 교차검증의 존재 이유다).

3\. \*\*diff가 아니라 상호작용 면(surface)을 스코프로\*\*: 기존 코드와 공존하는 기능은 "내 새 파일" 말고 \*\*"이 변경이 함께 도는 전체 계층과 충돌·중복·모순하는지"\*\* 를 감사시킨다. 상호작용 버그는 diff 밖에 산다.

4\. \*\*닫힌 루프 검증\*\*: 기능이 \*\*내보내는 산출물이 곧 입력이 되는 경우\*\*, 내보낸 모든 산출물을 다시 입력으로 먹여 전 게이트를 통과하는지 테스트한다. 자기모순은 여기서만 잡힌다.



> 초록불은 결승선이 아니라 "더 세게 찔러라"는 신호다. \*\*독립적 적대자(codex의 적대 감사 + Claude가 저작하지 않은 입력)가 못 깨뜨릴 때까지\*\* 반복한다.

```bash

command -v codex \&\& codex --version
```

\## 2. 표준 호출 (copy-paste)



```bash

codex exec --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox \\

&#x20; "<검증 프롬프트 — 아래 템플릿 참고>" < /dev/null

```



\*\*플래그 의미\*\*

| 플래그 | 이유 |

|--------|------|

| `exec` | 비대화형 1회 실행 모드 (TUI 안 띄움) |

| `--skip-git-repo-check` | 더티 작업 트리에서도 실행 허용 |

| `--dangerously-bypass-approvals-and-sandbox` | OS 샌드박스 헬퍼가 환경에 따라 깨져 있을 수 있어 샌드박스를 끄고 실행. 대신 프롬프트의 "수정 금지" 지시 + `git status` 안전망으로 통제 (§5) |

| `< /dev/null` | \*\*stdin을 닫는다.\*\* 안 닫으면 codex가 stdin 대기 상태로 무한 대기할 수 있음 |



필요 시 `-c 'mcp\_servers.<name>.enabled=false'` 로 이번 검증에 불필요한 MCP 서버를 개별적으로 끌 수 있다(전역 config는 건드리지 않음). 생략해도 결과 자체는 동일하고, 로그만 지저분해진다.



\*\*모델\*\*: `-m`을 주지 않으면 `\~/.codex/config.toml`의 기본 모델이 쓰인다. 계정에서 쓸 수 있는 최상위 모델 조합을 기본값으로 설정해두는 것을 권장한다.



실행 \*\*전후로 비교\*\* (전체 클린 여부가 아니라 \*델타\*만 본다):

```bash

git status --porcelain > /tmp/codex\_pre.txt        # codex 실행 전 baseline 스냅샷

codex exec ... < /dev/null                          # 검증 실행

git status --porcelain | diff /tmp/codex\_pre.txt -  # 델타 = codex 실행 중 생긴 변경 후보

```

델타가 \*\*이번 step 대상 파일 밖\*\*이면 codex가 아니라 사용자 병행 작업일 공산이 크다 → §4b 판단.

\## 3. 검증 프롬프트 템플릿



```

읽기 전용 검증 작업이다. 어떤 파일도 수정하지 마라.



\[목표] <이 step이 달성하려던 것 한 줄>



\[검증 기준] 아래를 각각 확인하라:

1\. <구체·기계적으로 확인 가능한 조건 1>

2\. <조건 2 — 예: 특정 빌드/테스트 명령이 통과>

3\. <조건 3 — 예: 특정 함수/엔드포인트/스키마가 존재하고 \~하게 동작>



\[출력] 각 기준의 통과 여부를 한 줄씩 적고,

마지막 줄에 정확히 'VERDICT: PASS' 또는 'VERDICT: FAIL (사유)' 만 출력하라.

```



원칙:

\- 기준은 \*\*기계적으로 확인 가능\*\*해야 한다(파일/함수/스키마 존재, 빌드·테스트 통과, 특정 문자열 부재 등). "예쁜가?" 같은 주관 기준 금지.

\- 빌드/테스트 실행을 시키면 codex가 직접 돌려서 결과로 판정한다(읽기만으로 부족할 때).

\## 4. step 진행 루프



> 이 루프의 실행 주체는 기본적으로 \*\*step 담당 subagent\*\*다(§4c). 오케스트레이터가 직접 돌리는 건 작은 단발 작업일 때뿐이다. 아래 "Claude"는 그 step을 실행 중인 에이전트(대개 subagent)를 뜻한다.



1\. Claude가 step 구현 → 자체 빌드로 1차 확인.

2\. codex 실행 전 `git status` baseline 스냅샷(§2).

3\. 해당 step의 acceptance criteria로 \*\*codex 검증 호출\*\*(§2).

4\. `VERDICT: PASS` + (델타에 \*\*step 대상 파일\*\*에 대한 codex의 의도치 않은 수정 없음):

&#x20;  - a. \*\*step 대상 파일만 명시적으로\*\* `git add <files>` 후 커밋. 메시지에 step 번호·목표 명시.

&#x20;    무관한 사용자 변경(병행 작업)은 \*\*절대 staging 금지\*\*.

&#x20;  - b. \*\*곧바로 다음 step으로 진행한다. "계속할까요?"라고 묻지 않는다.\*\* (이미 전체 진행을 위임받았다는 전제)

5\. `VERDICT: FAIL` → 사유를 보고 수정 후 3번 재실행. (Claude가 임의로 "됐다" 하지 않는다.)



\### 진행 정책 (커밋·자동 진행)



\- \*\*step별 커밋\*\*: PASS 받은 step은 그 즉시 대상 파일만 커밋한다. 한 step = 한 커밋(원칙).

\- \*\*묻지 않고 계속\*\*: PASS면 사용자 확인 없이 다음 step을 바로 시작한다. 진행 자체를 멈추고 묻는 건 아래 \*진짜 멈춰야 할 때\*로 한정한다.

\- \*\*push\*\*: 매 step push하지 않는다. 기능이 일관된 마일스톤에 도달했거나 사용자가 요청할 때 push. (미완 기능을 공유 브랜치에 매 step 흘리지 않기 위함)

\- \*\*진짜 멈춰야 할 때만 사용자에게 묻는다\*\*:

&#x20; 1) 설계가 갈리는 진짜 모호함(코드/맥락으로 못 정함), 2) 같은 step이 FAIL 반복(2\~3회)으로 막힘,

&#x20; 3) 되돌리기 어렵거나 외부로 나가는 작업(force push·삭제·배포 등). 그 외에는 멈추지 않는다.

\## 4b. 안전망 운용 — 과반응 금지 (중요)



codex 실행 후 `git status`에 변경이 보여도 \*\*전부 codex 탓이 아니다.\*\* 사용자는 그 사이

다른 파일을 병행 편집할 수 있다. 다음 절차로 \*\*귀속(attribution)\*\* 부터 판단한다:



1\. \*\*델타가 step 대상 파일인가?\*\* (이번에 내가 만지는 소스 + codex가 빌드/검사한 파일)

&#x20;  - 예 → codex가 건드렸을 수 있음. 내용 확인 후 필요시 되돌림.

&#x20;  - 아니오(무관한 문서·다른 기능·사용자의 알려진 WIP) → \*\*codex 아님.\*\* 그대로 둔다. 되돌리거나 캐묻지 않는다.

2\. 애매하면 \*\*사용자에게 단정 짓지 말고\*\* "이건 의도한 변경인가요?"로 가볍게 확인. \*codex가 망가뜨렸다고 단정 보고 금지.\*

3\. 커밋 시에는 어차피 \*\*step 대상 파일만 명시적으로 `git add`\*\* 하므로, 무관한 변경은 자연히 섞이지 않는다.



> 실제로, codex 검증 후 다수의 파일 변경이 보였지만 알고 보니 사용자가 별도로 진행한 무관한 작업(다른 기능/문서 정리)이었던 사례가 있었다. step 대상 파일이 아니면 스코프 밖 → codex 무관. 이런 걸 codex 탓으로 오인하지 말 것.

\## 4c. subagent 위임 모드 — step 실행의 기본형



step 작업은 오케스트레이터(메인 세션)가 직접 하지 않고 \*\*step(또는 작업 묶음) 담당 subagent에게 위임\*\*한다. subagent가 구현부터 codex 검증·커밋까지 §4 루프 전체를 자기 턴 안에서 완주하고, 오케스트레이터는 계획·투입·독립 검증·다음 step 투입만 맡는다.



\### 3계층 역할 분리



| 계층 | 하는 일 | 하지 않는 일 |

|------|---------|--------------|

| 오케스트레이터(메인) | step 분할, acceptance criteria 저작, subagent 투입, 보고의 \*\*git 독립 검증\*\*, 다음 step 투입 | 직접 구현 (컨텍스트를 계획·검증에 아낀다) |

| subagent | step 구현 → 빌드/테스트 → codex 호출 → FAIL 수정·재검증 → PASS 시 명시 pathspec 커밋 → 결과 보고 | 판정(self-judge), 스코프 밖 파일 접촉, 사용자에게 직접 질문 |

| codex | `VERDICT: PASS\|FAIL` 판정 | 구현·수정 |



핵심: \*\*판정 권한은 여전히 codex에만 있다.\*\* subagent도 Claude이므로 self-judge 금지가 그대로 적용된다. subagent는 codex의 VERDICT \*\*원문(마지막 줄)을 보고에 포함\*\*해야 하며, "codex 검증 통과했다"는 요약만으로는 검증된 것으로 인정하지 않는다.



\### subagent 투입 프롬프트 템플릿 (필수 요소 전부 포함)



```

\[step 목표] <한 줄>

\[대상 파일] <명시 — 이 밖의 파일은 접촉 금지>

\[acceptance criteria] <기계적으로 확인 가능한 조건들 — codex 프롬프트에 그대로 쓸 것>



\[필수 규칙]

1\. 이 문서(codex 가이드)를 먼저 읽고 §2 호출 형식·§3 프롬프트 템플릿·§4 루프를 그대로 따르라.

2\. codex·빌드·테스트는 전부 \*\*포그라운드로 실행\*\*하라. 백그라운드 실행 후 알림 대기 금지.

&#x20;  테스트는 비대화형 1회 실행 모드로 대상 범위만 좁혀 돌려라.

3\. codex에 판정 기준을 `git diff --cached --name-only`(스테이징된 것)로 선고지하라.

&#x20;  워킹트리의 병행 더티 파일은 판정 대상이 아니다.

4\. 줄바꿈 자동변환 환경(core.autocrlf 등)이라면 바이트/내용 비교는 저장소 blob 기준으로 하라

&#x20;  (워킹트리 개행 대조는 오탐).

5\. PASS 후 커밋은 \*\*대상 파일만 명시 pathspec으로\*\* `git add`. 그 외 파일 staging 절대 금지.

6\. FAIL이면 수정 후 재검증. 같은 step FAIL 2\~3회 반복이거나 설계가 갈리는 모호함이면

&#x20;  \*\*더 진행하지 말고 그 상태 그대로 보고하라\*\* (사용자에게 묻지 말 것 — 판단은 오케스트레이터가 한다).



\[보고 형식] step별로: 커밋 해시 / codex VERDICT 원문 / FAIL이 있었다면 사유·수정 내역 / 이월 발견사항.

```



프롬프트에 왜 저 항목들이 필수인가 (전부 실제 겪은 사고 유형):



\- \*\*포그라운드 강제(2)\*\*: subagent가 codex·테스트를 백그라운드로 돌리고 알림을 기다리다 턴을 끝내는 패턴이 반복적으로 관찰됐다. 프롬프트에 명시하면 무정지 완주한다.

\- \*\*`git diff --cached` 선고지(3)\*\*: 사용자 병행 편집 더티 파일을 codex가 "변경 범위"로 오판해 FAIL하는 사례가 있었다. §4b 과반응 문제는 codex 쪽에서도 난다.

\- \*\*blob 기준 비교(4)\*\*: 줄바꿈 자동변환 환경에서 워킹트리 개행 vs 저장소 blob을 비교하는 바이트 동일성 검증이 헛 FAIL을 낸 사례가 있었다.



\### 순차 투입 — step subagent 병렬 금지



step subagent는 \*\*한 번에 하나만\*\* 투입한다. codex의 git-status 안전망(§2)과 명시 pathspec 커밋 위생이 전부 워킹트리 상태를 전제하므로, 같은 저장소에 subagent를 병렬로 풀면 서로의 델타를 오염시켜 안전망 자체가 무의미해진다. (사용자의 병행 세션은 §4b대로 귀속 판단으로 흡수하지만, 우리 스스로 병렬을 만드는 것은 금지.)



\### 오케스트레이터의 독립 검증 — 자기보고를 믿지 마라



subagent 보고를 받으면 \*\*git으로 대조한 뒤에만\*\* 그 step을 완료 처리한다:



1\. `git log --oneline <투입 전 HEAD>..HEAD` — 커밋 수·메시지가 보고와 일치하는가. (자기보고 커밋 수가 실제와 달랐던 사례가 있다 — 수치는 항상 git이 정본.)

2\. `git show --stat <해시>` — 각 커밋에 스코프 밖 파일이 섞이지 않았는가.

3\. 보고에 step별 codex VERDICT \*\*원문\*\*이 있는가. 없으면 미검증으로 간주하고 오케스트레이터가 직접 §2로 codex를 재실행해 판정을 받는다.

4\. 빌드/타입체크 게이트를 오케스트레이터가 한 번 더 돌린다 (번들러 빌드가 타입체크를 생략하는 프로젝트라면 타입체커 직접 실행 필수).



\### subagent가 도중에 죽었을 때



subagent가 최종 보고 전에 종료(크레딧 소진·프로세스 사망)돼도 \*\*커밋이 진실\*\*이다. `git log`로 어디까지 PASS·커밋됐는지 재구성하고, 미완 부분만 acceptance criteria를 조정해 새 subagent를 재투입한다. VERDICT 원문이 유실됐더라도 커밋 내용·빌드는 사후 git/실행 검증으로 복원할 수 있다.

\## 5. 함정 \& 트러블슈팅



| 증상 | 원인 | 대응 |

|------|------|------|

| stdin 대기 메시지 후 무한 대기 | stdin 미닫힘 | `< /dev/null` 추가 |

| Windows 샌드박스 헬퍼 실행 실패 (`orchestrator\_helper\_launch\_failed` 등) | `--sandbox read-only`가 OS 샌드박스 헬퍼를 못 찾음 | `--sandbox read-only` 쓰지 말고 `--dangerously-bypass-approvals-and-sandbox` 사용 |

| MCP 관련 transport/연결 오류 로그 | codex 설정에 등록된 로컬 MCP 서버가 안 떠 있음 | \*\*대개 무해\*\*(codex가 일반 셸 명령으로 폴백해 정상 동작). 로그를 깔끔히 하려면 §2처럼 해당 서버만 `-c` 로 끄기 |

| 토큰 사용량 비정상 폭증 | 깨진 샌드박스에서 재시도 thrash | 샌드박스 플래그 교정으로 해결됨 |



> 정리: \*\*OS 샌드박스에 기대지 않는다.\*\* "수정 금지" 프롬프트 지시 + 실행 후 `git status` 대조가 안전망이다.

> MCP 노이즈는 결과에 영향이 없다 — 필요 서버만 끄거나 그냥 무시하면 된다.
